# WorkTrace 员工隐私说明

> 按 WorkTrace 当前代码核对，更新于 2026-10-02。

这份说明是写给使用 WorkTrace 的员工看的，重点只有一句话：

WorkTrace 的目标是帮你回顾你自己的工作事项，不是偷偷收集你的个人隐私。

## 1. 它会做什么

- 根据目标日期里你发过消息或做过 reaction 的记录定位飞书会话，再读取这些会话的当天消息与必要关联上下文；reaction 搜索有分页数量限制，不保证发现全部 reaction
- 提取和你自己直接相关的工作事件
- 在你本地生成一份 Markdown 文件
- 默认通过飞书机器人先把这份文件发给你自己

## 2. 它默认不会做什么

- 不会默认直接发给领导
- 不会建立全量聊天长期档案，但运行中的断点缓存和调试文件有本地留存边界，见第 4 节
- 最终 Markdown 不设置群名、open_id、消息 ID、会话 ID 或原会话参与人名单字段；正文中的常见飞书内部 ID 会替换，文件标题和 URL 不属于全面匿名处理
- Markdown 隐藏信息保存参与方式英文键、SHA-256 消息证据指纹、同日会话指纹、文件标识、内容指纹、人工修订类型，以及可选的来源事件 ID 和上游来源负责人，用于回读和多人汇总；不保存原始消息 ID、会话 ID 或用户 ID。哈希不是加密，也不使包含姓名、事件内容和 URL 的整个文件匿名
- 事件正文只在责任分工、任务指派、确认沟通对象等确有必要时保留姓名
- 代码不会仅凭私聊属性排除会话：有本人参与的私聊也可能被读取并进入模型上下文。需要排除时使用本地会话黑名单，不能依赖程序自动识别“私人聊天”

## 3. 你需要知道的真实边界

- WorkTrace 会通过你本机上的 `lark-cli` 读取聊天
- WorkTrace 会把必要的精简文本、会话名、发送者信息、消息和会话标识、链接 URL/标题、附件文件名发送到选定模型。默认 `WORKTRACE_LLM_MODE=codex_with_fallback` 使用 Codex，已配置 Online 时，可重试技术失败或任务质量重试用尽后可能把当前请求发送到 Online；`online_only` 从一开始就只用 Online，文字、图片摘要和诊断报告均不调用 Codex
- 为补齐 reply/quote 直接关系或模型请求的相邻上下文，系统可能临时读取并发送目标日期之外的直接关联消息；事件日期仍固定为目标日期
- 最终贡献核对可能补入候选来源切片及已选证据消息内、同会话较早的非空完整相同正文作为背景；不为此扩展到切片外，也不把相同正文直接当作贡献结论
- 图片摘要启用时，本人发送或本人 reply/quote 直接关联的图片会按大小限制处理；其他图片受数量和大小限制，并只在模型明确请求时处理
- 模型明确请求时，指定文本附件或飞书文档正文也可能发送到上述模型线路
- 读取飞书文档标题时，程序可能自动调用完整文档读取接口；文档正文进入模型上下文则由明确的补读请求控制，不能理解成请求前完全不读取文档
- 所以你应当确认仓库本地模型模式，以及当前模式使用的 Codex 模型/推理强度或 Online 地址、模型和密钥，都是自己认可的配置

这意味着它不是“绝对不外发任何内容”的纯本地方案。  
如果你不认可某个模型服务，就不要使用那套配置。

## 4. 当前项目怎么尽量减少隐私暴露

- 以与你直接相关的事项作为事件保留条件，但分析输入也包含他人的必要上下文；敏感词和排除词过滤不等于发送前全面脱敏
- 个人产出公开字段包括日期、事件标题、主要动作、内容、具体对象、本人参与方式、保留理由、保留依据和涉及文件；人工修订时另显示修订标记。团队汇总还显示来源人员和有值时的来源负责人
- Online 主线路或备用线路追加 `/no_think`；有效配置 `reasoning_effort=none` 时（当前默认），按协议在请求体使用 `reasoning.effort=none` 或 `thinking.type=disabled`。关闭字段取决于实际运行配置；Codex 不追加该文本
- 固定结构任务采用同一份严格契约：Online 使用原生 Function Calling，Codex 以完整契约提示词和同一 output-schema 提交一次参数 JSON
- 消息正文中的裸链接会压缩为占位文本，但链接 URL、标题和临时引用 ID 仍进入模型输入；文档正文向模型补充的条件见第 3 节。Markdown 链接仅替换已知敏感查询参数，不保证正文、标题和任意 URL 已完全脱敏
- 可以复制 `config/conversation_blacklist.example.json`，通过仅保存在本机的 `config/conversation_blacklist.json` 排除指定会话的后续读取和分析。飞书全局搜索仍可能返回该会话消息，程序在本地结果中排除，不代表服务端从未返回过它
- 正式运行默认不开启完整调试 trace，但会在 `data/cache/llm/YYYY/MM/YYYY-MM-DD/` 写入含分析输入、消息上下文和结果的断点缓存。Markdown 写入成功后清除当天缓存；失败时可能留存，`--resume` 可复用它，普通重新运行会先清理该日缓存和旧个人输出
- `--debug-output` 另保存裁剪后的上下文、prompt、事件和模型输出；旧调试文件不会因后续手工删事件自动清除，只应临时开启并在使用后自行清理
- Codex 每次调用在独立临时目录中运行，提示词通过 stdin 输入，Schema、结果和图片副本结束即删除；子进程环境变量使用允许名单，`read-only` 只表示写保护，不是操作系统级读取隔离
- Codex JSON 事件中出现 Shell、MCP、Web 或其他工具调用时，当前请求会按协议违规处理
- 多人汇总会发送已收集 Markdown 中的事件正文、必要来源姓名和临时 draft ID；共同消息、共同文件和同日会话只转换成临时关系，不发送原始消息 ID、会话 ID 或长指纹
- 开启调试的 CLI 在业务运行结束后额外发起报告分析请求，可能按模式重试或使用备用。报告模型只接收 Python 整理的编号状态、数量、墙钟耗时、token、重试、线路、写入和送达事实，不接收聊天、事件文字、prompt、原始模型返回或日志原文
- 可分享的诊断材料只有 `data/debug/support_reports/worktrace-support-<随机编号>.md`；完整 `data/debug` 目录不能外发，也不能由 Codex 自行整理成外发材料
- 安全报告写入前按 `config/support_report.json` 扫描用户目录、飞书 ID、网址、联系方式、日期、文件名和指定密钥样式；命中时不写该报告。当前没有通用的姓名识别规则，也不能把模式扫描通过理解为绝对不存在隐私
- 调试账本 `llm_calls.json` 会保留调用编号、严格契约、最终提示词、后端、模型、推理强度、切换原因、原始结果和 Python 校验状态；不会保存密钥、认证文件、个人 Codex 配置、完整环境变量、图片内容或原始 Codex JSONL

## 5. 你有自主权

- 默认启用送达且成功时，你会先收到机器人发给自己的 Markdown；关闭 `config/self_delivery.json`、多人使用 `--offline` 或送达失败时，先查看本地文件和 CLI 送达状态
- 你可以先审阅、修改，再决定是否转发
- 诊断报告不会自动上传或发送；需要排障时只发送 CLI `support_report.path` 指向的单个 Markdown，不发送 ZIP 或原始 trace
- 如果你对配置或隐私边界有疑虑，应先停下来确认，而不是直接运行
- 从文件删除事件只影响本次读取和后续输出，不追溯清理旧文件、缓存、trace 或已经发送的副本；其他来源仍包含同一事项时也可能再次进入汇总
