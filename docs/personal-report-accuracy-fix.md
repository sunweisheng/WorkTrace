# 个人报告准确性修复记录

## 问题与修复

原报告存在知识查询误写为实质审批、他人交付误标本人主责执行，以及同一事件文件名重复展示的问题。

- 业务规则在 `config/retention_policy.json` 中补充：保留理由须符合真实工作性质；没有业务结果的纯知识查询不保留；本人角色依据本人实际动作判断，简单接收使用 `response_only`。
- 复用已有的 `personal_group_render`，依据原消息和已经补读的相关附件、在线文档内容，同时核对正文、主要动作、具体对象、保留理由、保留依据和本人参与方式。Python 检查字段、枚举、消息覆盖和本人证据后统一采用结果，不增加全日模型阶段，也不按关键词解释聊天。
- 本人证据与正文来源分别保存时，两者的原消息共同进入核对；角色只能引用本人证据。最终来源记录包含实际引用的本人消息。
- 提炼缓存保存实际使用的证据片段，续跑时恢复补读消息及附件、文档正文；缺少完整证据的旧缓存重新请求，避免仅恢复候选后丢失事实依据。
- Markdown 文件列表按脱敏后的名称和地址去重；同名无地址文件显示一次，同名不同地址分别显示。内部附件 ID 和文件标识继续保留，旧 v3 内容指纹兼容读取，真实人工修改仍会标记。
- 当前局部质量重试与主备请求用尽后，最终核对仍失败则整次生成失败。调试记录保留成功结果与失败原因，不会写入或发送未经核对的报告。

## 4.1.2 之后的高优先级补充修复

家庭测试发现：他人先发送数据和附件，本人确认后再次发送相同正文，仍可能被写成“本人完成汇总、主责执行”。最终核对现在先声明本人动作，再由正文、主要动作和角色共同引用这些动作；Python 检查声明之间的一致性。动作含义与允许角色放在配置中，接收和转发不支撑主责；明确承担任务不能写成已经完成。相关证据切片中较早的完整相同正文同步补入核对，空附件正文、压缩后相同及其他切片的旧消息不补入。

本次只修复个人贡献判断、Windows 测试兼容和诊断失败说明。旧发布记录和历史日报不改写，部署后的完整业务运行需另外验证。
