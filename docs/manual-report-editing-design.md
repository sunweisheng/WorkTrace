# WorkTrace 日报手工编辑支持设计

## 1. 目标

WorkTrace 生成的个人日报和上游汇总 Markdown 允许通过 Codex、文本编辑器或其他 Markdown 编辑器进行调整。调整后的文件只要仍能识别出合法事件，就可以参与多人合并。

支持三种结果：

- 删除事件：直接删除，不保留删除记录。
- 新增事件：标记为人工新增。
- 修改事件：标记为人工修改。

如果隐藏信息被外部编辑器删除或损坏，但可见事件字段仍完整，则标记为人工修订且类型无法确认。修订标记只用于说明来源，不降低事件在多人合并中的参与资格。

## 2. 隐私边界

删除即遗忘。系统不得为已经删除的事件保存或输出以下信息：

- 事件 ID
- 标题、正文、具体对象或其他业务字段
- 消息、会话或文件指纹
- 删除数量、删除时间或删除类型
- 墓碑、占位记录或日报级原始事件清单

多人合并、调试 trace、诊断报告和上游汇总都不得传播删除痕迹。Markdown 中的 `event_count` 只表示当前仍存在的事件数量。来源文件声明数量与实际解析数量的差值不再作为审计字段保存，也不用于推断删除行为。

尾部事件块损坏属于文件结构错误，不属于正常删除。结构错误可以保留必要的错误类型和当前有效事件数量，但不得复制损坏块正文。

## 3. 事件级来源信息

新版 `merge_meta` 使用 version 3。每条仍存在的事件独立保存：

```json
{
  "version": 3,
  "manual_edit_type": "",
  "source_manual_edit_types": [],
  "content_fingerprint": "sha256:..."
}
```

字段含义：

- `manual_edit_type`：当前事件本身的手工编辑类型。
- `source_manual_edit_types`：团队汇总事件从下级来源继承的手工编辑类型。
- `content_fingerprint`：生成时对当前事件可见业务字段计算的稳定 SHA-256 指纹。

允许的手工编辑类型由 `config/event_metadata.json` 配置：

- `manual_added`
- `manual_modified`
- `manual_unknown`

不得把内容指纹当作消息或会话证据。内容指纹只用于判断仍存在的事件是否被外部编辑器修改。

## 4. 内容指纹

Python 对下列规范化字段计算内容指纹：

- 日期
- 标题
- 主要动作
- 内容
- 具体对象
- 本人参与方式或协作方式
- 保留理由
- 保留依据
- 来源人员和来源负责人
- 涉及文件的公开标题与脱敏 URL

编号、事件顺序、空行、Markdown 缩进、隐藏来源 ID 和修订标记不进入内容指纹。所有比较和数量统计由 Python 完成，大模型不参与。

## 5. 外部编辑识别

### 5.1 删除

事件块从文件中消失后，该事件及其隐藏信息同时消失。系统不比较日报级原始清单，不生成删除标记，也不在任何输出中说明发生过删除。

### 5.2 修改

事件保留 version 3 隐藏信息，但当前可见字段计算出的指纹与 `content_fingerprint` 不同，则设置 `manual_edit_type=manual_modified`。重新渲染时保留最初的内容指纹和人工修改状态，使标记在后续多级汇总中持续存在。

### 5.3 新增

在事件列表中新增的标准 Markdown 事件没有可信的生成指纹时，设置 `manual_edit_type=manual_added`。Python 为它生成稳定事件 ID。新增事件可以没有消息和会话指纹。

标准可见结构至少包含三级编号标题及日期、内容、具体对象、保留理由、保留依据和涉及文件字段。字段名称与修订显示名称从配置读取；随意插入的普通段落不视为事件。

### 5.4 类型无法确认

已有事件标记仍在，但 `merge_meta` 被删除、损坏，或旧 version 2 事件缺少会话证据时，设置 `manual_edit_type=manual_unknown`。正文结构合法时允许参与多人合并。

有效 version 1 历史文件仍按旧版来源处理，不自动声称它经过人工修改。

## 6. Markdown 展示

未修改的自动生成事件不增加可见字段。存在手工编辑类型时，在事件中显示配置定义的修订字段，例如：

```markdown
- **修订标记**: 人工新增
```

团队汇总事件如果包含下级人工新增、人工修改或类型无法确认的来源，也显示对应标记。标记在部门到中心的再次汇总中去重并继续保留。

删除事件不显示任何标记。

## 7. 多人合并规则

来源事件满足以下任一条件即可进入多人合并：

- 有合法 version 2 或 version 3 会话指纹。
- 有合法的 `manual_edit_type`。
- 有从下级汇总继承的 `source_manual_edit_types`。

人工新增事件不参与共同消息、共同会话或共同文件的确定性关系发现，但仍按标题、正文、具体对象和业务关系进入模型判断。人工修改事件保留原有消息、会话和文件指纹用于候选发现，同时明确携带人工修改标记。

缺少会话证据且没有合法修订类型的 version 1 来源仍停止合并并要求重新生成。

## 8. 来源审计

来源审计只保存当前有效状态，包括当前解析事件数、当前模型输入事件数、结构错误和过滤数量。以下字段从新审计输出中移除：

- `declared_event_count`
- `event_count_delta`

正常删除不会产生 warning。`parsed_event_count` 只表示当前有效事件数量，不表达历史变化。

## 9. 兼容策略

- 新生成的个人和团队 Markdown 写 version 3。
- version 2 且会话证据完整的文件继续正常参与多人合并，但无法自动识别其正文是否在生成后被修改。
- version 2 中单个事件缺少会话证据时，按 `manual_unknown` 处理并允许合并。
- version 1 继续读取，但不会自动升级或补造会话证据。
- 不批量改写历史文件。

## 10. 验收要求

- 删除事件后，文件、trace、CLI JSON 和汇总 Markdown 中不存在被删事件信息或删除标记。
- 修改 version 3 事件任一公开业务字段后，解析结果标记为人工修改。
- 新增带标准可见字段但没有 HTML 注释的事件后，解析结果标记为人工新增。
- 损坏隐藏信息但保留合法正文时，解析结果标记为类型无法确认。
- 三种仍存在的修订类型都能通过离线和普通多人合并。
- 部门汇总中的修订标记能继续进入中心汇总。
- 旧 version 2 正常来源保持兼容。
- 统计和指纹均由 Python 确定性计算。
