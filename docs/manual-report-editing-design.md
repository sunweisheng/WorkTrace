# WorkTrace 日报手工编辑支持设计

> 状态：4.1.0 已实现的 Markdown 读取与人工修订规则；2026-10-02 按代码和现有测试核对。

## 1. 目标

WorkTrace 生成的个人日报和上游汇总 Markdown 允许通过 Codex、文本编辑器或其他 Markdown 编辑器进行调整。调整后的文件只要仍能识别出合法事件，就可以参与多人合并。

支持三种结果：

- 删除事件：直接删除，不保留删除记录。
- 新增事件：标记为人工新增。
- 修改事件：标记为人工修改。

如果事件起始标记仍在、隐藏合并信息被外部编辑器删除或损坏，则按人工修订且类型无法确认处理。修订标记提供来源资格，事件仍需通过敏感词、排除词和具体对象、保留理由、保留依据门槛；不保证任意编辑内容都被保留。

## 2. 隐私边界

本次读取只处理来源文件中仍存在的事件，不比较历史事件清单，也不为本次文件中已删除的事件新增以下信息：

- 事件 ID
- 标题、正文、具体对象或其他业务字段
- 消息、会话或文件指纹
- 删除数量、删除时间或删除类型
- 墓碑、占位记录或日报级原始事件清单

后续多人合并、该次 trace 和输出不产生删除痕迹。已有其他来源文件、旧 trace、此前生成或送达的文件不随本次编辑追溯清理；其他输入仍含同一事项时，本次汇总也可能保留该事项。生成时的 `event_count` 表示当时事件数量，外部编辑后可能未更新；读取器不以它推断删除，也不保存声明数量与实际解析数量的差值。

尾部事件块损坏属于文件结构错误，不属于正常删除。允许部分读取时，结构错误可以保留文件名、损坏事件 ID、必要错误类型和当前有效事件数量，但不复制损坏块正文。

## 3. 事件级来源信息

新版 `merge_meta` 使用 version 3。每条仍存在的事件独立保存：

```json
{
  "version": 3,
  "manual_edit_type": "",
  "source_manual_edit_types": [],
  "content_fingerprint": "sha256:..."
}
```

字段含义：

- `manual_edit_type`：当前事件本身的手工编辑类型。
- `source_manual_edit_types`：团队汇总事件从下级来源继承的手工编辑类型。
- `content_fingerprint`：生成时对当前事件可见业务字段计算的稳定 SHA-256 指纹。

允许的手工编辑类型由 `config/event_metadata.json` 配置：

- `manual_added`
- `manual_modified`
- `manual_unknown`

不得把内容指纹当作消息或会话证据。内容指纹只用于判断仍存在的事件是否被外部编辑器修改。

## 4. 内容指纹

Python 对下列规范化字段计算内容指纹：

- 日期
- 标题
- 主要动作
- 内容
- 具体对象
- 本人参与方式或协作方式
- 保留理由
- 保留依据
- 来源人员和来源负责人
- 涉及文件的公开标题与脱敏 URL

编号、事件顺序、隐藏来源 ID 和修订标记不进入内容指纹；空行等格式变化只有不改变解析字段时才不影响指纹。字段使用当前渲染的中文标签、内部 ID 替换、句末文字规范化和 URL 敏感参数替换后计算，不是对任意 Markdown 格式进行语义等价比较。所有比较和数量统计由 Python 完成，大模型不参与。

## 5. 外部编辑识别

### 5.1 删除

事件块从文件中消失后，该事件及其隐藏信息同时消失。系统不比较日报级原始清单，不生成删除标记，也不在任何输出中说明发生过删除。

### 5.2 修改

事件保留有效 version 3 隐藏信息，且尚无合法 `manual_edit_type` 时，当前解析字段计算出的指纹与 `content_fingerprint` 不同，则设置 `manual_edit_type=manual_modified`。已有合法人工类型时保留该类型，不进一步改判。对同一事件重新渲染会保留原指纹和标记；多人汇总产生新事件时计算新指纹，并通过 `source_manual_edit_types` 继承来源修订类型。

识别依据是解析后的字段，并非对所有可见文本做差异检查。例如保留隐藏 `retention_reason` 时，可见“保留理由”由隐藏枚举优先解析；只改该行未必触发人工修改。来源负责人可见字段为空时也会回读隐藏列表。应同步维护相应机器字段，或通过合法标准事件结构重新编辑后检查回读结果。

### 5.3 新增

没有事件 HTML 起始标记的标准 Markdown 事件设置 `manual_edit_type=manual_added`，Python 根据日期、标题、正文、对象和出现位置生成事件 ID；复制已有块造成重复事件 ID 时，后出现的块也按人工新增处理。这两种情况会丢弃复制来的隐藏证据和上游事件 ID、负责人，避免冒用原事件来源。新增事件可以没有消息和会话指纹；有独立起始标记但无有效隐藏信息时按下一节的 `manual_unknown` 处理。

标准可见结构至少包含三级编号标题及日期、内容、具体对象、保留理由、保留依据和涉及文件字段。读取器使用代码中列出的标准字段前缀，字段从行首开始，业务内容按对应单行读取；不是任意字段名或任意排版都能识别。人工类型与修订显示名称来自 `config/event_metadata.json`；随意插入的普通段落不视为事件。

### 5.4 类型无法确认

已有事件标记仍在，但 `merge_meta` 被删除、损坏，或 version 2/3 事件缺少会话证据且没有合法当前/继承修订类型时，设置 `manual_edit_type=manual_unknown`。损坏隐藏信息另记 warning；仍需通过后续来源过滤才能参与模型合并。

有效 version 1 历史文件仍按旧版来源处理，不自动声称它经过人工修改。

## 6. Markdown 展示

未修改的自动生成事件不增加可见字段。存在手工编辑类型时，在事件中显示配置定义的修订字段，例如：

```markdown
- **修订标记**: 人工新增
```

团队汇总事件如果包含下级人工新增、人工修改或类型无法确认的来源，也显示对应标记。标记在部门到中心的再次汇总中去重并继续保留。

删除事件不显示任何标记。

## 7. 多人合并规则

来源事件满足以下任一条件即可进入多人合并：

- 有合法 version 2 或 version 3 会话指纹。
- 有合法的 `manual_edit_type`。
- 有从下级汇总继承的 `source_manual_edit_types`。

无标记或重复 ID 的新增事件在首次读取时没有继承消息、会话、文件指纹，不用这些证据形成共同关系，但仍按标题、正文、具体对象进入模型判断；合法附件名称也可能进入候选复核。重新渲染时，有效文件 URL 会生成文件指纹，供后续汇总发现共同文件关系。有效 V3 中已带人工新增标记和合法指纹的事件，关系发现也不会单独排除它。人工修改继续保留原有合法指纹并携带修订标记，但原指纹不证明修改后的每句话都来自聊天。

缺少会话证据且没有合法修订类型的 version 1 来源仍停止合并并要求重新生成。

## 8. 来源审计

来源审计只保存当前有效状态，包括当前解析事件数、当前模型输入事件数、结构错误和过滤数量。以下字段从新审计输出中移除：

- `declared_event_count`
- `event_count_delta`

正常删除不会产生 warning。`parsed_event_count` 只表示当前有效事件数量，不表达历史变化。

## 9. 兼容策略

- 新生成的个人和团队 Markdown 写 version 3。
- version 2 且会话证据完整的文件继续正常参与多人合并，但无法自动识别其正文是否在生成后被修改。
- version 2 中单个事件缺少会话证据时，按 `manual_unknown` 处理并允许合并。
- version 1 继续读取，但不会自动升级或补造会话证据。
- 不批量改写历史文件。

## 10. 现有测试与验收边界

- 从本次来源文件删除事件后，本次解析和后续 trace、CLI JSON、汇总不新增该事件信息或删除标记；不要求追溯清理其他文件。
- 修改未带当前人工类型的 version 3 事件的解析业务字段后，指纹差异标记为人工修改；隐藏字段优先级见第 5 节。
- 新增带标准可见字段但没有 HTML 注释的事件后，解析结果标记为人工新增。
- 损坏隐藏信息但保留合法正文时，解析结果标记为类型无法确认。
- 三种仍存在的修订类型都能通过离线和普通多人合并。
- 部门汇总中的修订标记能继续进入中心汇总。
- 旧 version 2 正常来源保持兼容。
- 统计和指纹均由 Python 确定性计算。

读取识别场景见 `tests/unit/test_markdown_store.py`；缺少证据停止、V2 空会话兼容及部门到中心修订传递见 `tests/unit/test_collected_merge.py`。本次只核对文档与这些测试的内容，未重新执行真实日报、模型或送达验收。
